[#introduction]
== Introduction


Couchbase Lite for Java provides API support for secure, bidirectional synchronization of data changes between mobile applications and a central server database.
It does so by using a replicator to interact with Sync Gateway.

The replicator manages replication of documents and document changes between a source and a target database.
For example, it can replicate between a local Couchbase Lite database and a remote Sync Gateway database.
The Sync Gateway database maps to a bucket in a Couchbase Server instance in the cloud or on a server.

This page shows sample code and configuration examples covering the implementation of a replication using Sync Gateway.

Your application runs a replicator, also called a client.
The replicator starts a connection with Sync Gateway, also called a server.
It then participates in the replication of database changes to bring both local and remote databases into sync.

Subsequent sections provide additional details and examples for the main configuration options.

[#replication-concepts]
== Replication Concepts

Couchbase Lite allows for one database for each application running on the mobile device.
This database can contain one or more scopes.
Each scope can contain one or more collections.

To learn about Scopes and Collections, see xref:java:database.adoc[].

You can set up a replication scheme across these data levels:

Database:: Couchbase Lite syncs the `_default` collection.

Collection:: Couchbase Lite syncs a specific collection or a set of collections.

As part of the syncing setup, Sync Gateway must map the Couchbase Lite database to the corresponding database on Capella.


[#replication-protocol]
== Replication Protocol

[#scheme]
=== Scheme

Couchbase Mobile uses a replication protocol based on WebSockets for replication.
To use this protocol the replication URL should specify WebSockets as the URL scheme (see the xref:java:replication.adoc#lbl-cfg-tgt[] section below).

Incompatibilities::
The Couchbase Lite replication protocol is *incompatible* with CouchDB-based databases.
Couchbase Lite 2.x and later support only the new protocol, so you must run a version of Sync Gateway that supports it -- see xref:java:compatibility.adoc[Compatibility].

Legacy Compatibility::
Clients using Couchbase Lite 1.x can continue to use `http` as the URL scheme.
Sync Gateway 2.x and later automatically use:
* The 1.x replication protocol when a Couchbase Lite 1.x client connects through `\http://localhost:4984/db`
* The 2.0 replication protocol when a Couchbase Lite 2.0 client connects through `ws://localhost:4984/db`.

For more information, see the blog post https://blog.couchbase.com/data-replication-couchbase-mobile/[Introducing the Data Replication Protocol].

[#lbl-repl-ord]
=== Ordering

To optimize for speed, the replication protocol does not guarantee that documents arrive in a particular order.
Do not rely on document order, for example, when using replication or database change listeners.


[#scopes-and-collections]
== Scopes and Collections

Scopes and Collections allow you to organize your documents in Couchbase Lite.

When syncing, you can configure which collections to sync.

The collections specified in the Couchbase Lite replicator setup must exist on the Sync Gateway side, with identical scope and collection names.
Otherwise, the Couchbase Lite replicator returns an error when it starts.

During replication:

. If you update the Sync Gateway configuration or server to remove a collection that the replicator syncs, the client replicator goes offline and stops after the first retry.
The replicator reports an error.

. If you update the Sync Gateway configuration to add a collection to a scope that the replicator syncs, the replication ignores the new collection.
The new collection does not sync until you update the Couchbase Lite replicator configuration.

[#default-collection]
=== Default Collection

When you upgrade Couchbase Lite to 3.1, Couchbase Lite automatically migrates the existing documents in the database to the default collection.

This preserves backward compatibility with code written before 3.1.
When you set up the replicator with the database, the replicator syncs the default collection with the default collection on Sync Gateway.

[#lbl-cfg-keep-alive]
=== Retry Configuration


Couchbase Lite for Java replication retry logic provides a resilient connection.

The replicator minimizes the chance and effect of dropped connections by maintaining a heartbeat.
The heartbeat pings Sync Gateway at a configurable interval to keep the connection alive.

If the replicator detects a transient error, it tries to reconnect.
It stops only when it re-establishes the connection or the number of retries exceeds the retry limit.
The retry limit is 9 times for a single-shot replication and unlimited for a continuous replication.

On each retry, the interval between attempts increases exponentially, up to the maximum wait time limit of 5 minutes.

The REST API provides control over this replication retry logic using a set of configurable properties -- see: xref:java:replication.adoc#tbl-repl-retry[].

[#lbl-svr-auth]
=== Server Authentication

Define the credentials that the client app expects from the Sync Gateway server before it continues with the sync.

The client cannot authenticate the server if you turn off TLS.
When you enable TLS, which is the Sync Gateway default, the client must authenticate the server.
If the server cannot provide acceptable credentials, the connection fails.

Use `https://docs.couchbase.com/mobile/{major}.{minor}.{maintenance-java}{empty}/couchbase-lite-java/com/couchbase/lite/ReplicatorConfiguration.html[ReplicatorConfiguration]` properties https://docs.couchbase.com/mobile/{major}.{minor}.{maintenance-java}{empty}/couchbase-lite-java/com/couchbase/lite/ReplicatorConfiguration.html#setAcceptOnlySelfSignedServerCertificate-boolean-[setAcceptOnlySelfSignedServerCertificate] and https://docs.couchbase.com/mobile/{major}.{minor}.{maintenance-java}{empty}/couchbase-lite-java/com/couchbase/lite/ReplicatorConfiguration.html#setPinnedServerCertificate-byte:A-[setPinnedServerCertificate()], to tell the replicator how to verify server-supplied TLS server certificates.

* If there is a pinned certificate, nothing else matters: the server certificate must be identical to the pinned certificate.
* If there are no pinned certificates and https://docs.couchbase.com/mobile/{major}.{minor}.{maintenance-java}{empty}/couchbase-lite-java/com/couchbase/lite/ReplicatorConfiguration.html#setAcceptOnlySelfSignedServerCertificate-boolean-[setAcceptOnlySelfSignedServerCertificate] is `true`, the replicator accepts any self-signed certificate.
The replicator rejects certificates that are not self-signed, no matter who signed them.
* If there are no pinned certificates and https://docs.couchbase.com/mobile/{major}.{minor}.{maintenance-java}{empty}/couchbase-lite-java/com/couchbase/lite/ReplicatorConfiguration.html#setAcceptOnlySelfSignedServerCertificate-boolean-[setAcceptOnlySelfSignedServerCertificate] is `false`, the default, the client validates the server's certificates against the system CA certificates.
The root of the server's certificate chain must have a signature from one of the certificates in the system CA bundle.

.Losing access to a document through the Sync Function

Losing access to a document through the Sync Function also triggers the pull replication filter.

As a result, the local copy of the document becomes disjointed from the copy on Couchbase Server.

Pull replications do not receive further updates to the document stored on Couchbase Server.

[#lbl-repl-chan]
=== Channels

// include::ROOT:partial$replication-channels.adoc[]
By default, Couchbase Lite gets all the channels to which the configured user account has access.

This behavior is suitable for most apps that rely on
xref:sync-gateway::learn/authentication.adoc[user authentication]
and the
xref:sync-gateway::sync-function-api.adoc[sync function]

Optionally, you can specify a string array of channel names on the Couchbase Lite collection configuration object.
In this case, the replication from Sync Gateway pulls only documents tagged with those channels.

[#anchor-auto-purge-on-revoke]
=== Auto-purge on Channel Access Revocation

[CAUTION]
--
This is a Breaking Change at 3.0
--
[#new-outcome]
==== New Outcome

By default, when a user loses access to a channel, Couchbase Lite auto-purges all documents in that channel from the user's devices.
This does not apply to documents that also belong to any of the user's other channels.

[#prior-outcome]
==== Prior Outcome

Before this release, these documents remained in the local database.
Couchbase Lite auto-purged a document only when the user lost access to it because it no longer belonged to any of the user's channels.
Now, in addition to the 2.x auto-purge behavior, Couchbase Lite also auto-purges documents when the user loses access through channel access revocation.
This feature is on by default, but you can turn it off.

[#behavior]
==== Behavior

Users may lose access to channels in a number of ways:

* User loses direct access to channel

* An administrator removes the user from a role

* An administrator removes a channel from a role that the user holds

By default, when a user loses access to a channel, the next Couchbase Lite Pull replication auto-purges that channel's documents from the user's devices.
The replication does not purge documents that belong to any of the user's other channels -- see: xref:java:replication.adoc#tbl-revoke-behavior[].

Couchbase Lite does not auto-purge documents that exist in multiple channels belonging to the user unless the user loses access to all those channels.
This applies even if the user does not actively replicate those channels.

When auto-purge is `true`, users receive an `AccessRemoved` notification from the DocumentListener if they lose document access through channel access revocation.

*For permanent network errors*, such as `404` not found or `401` unauthorized, the replicator stops permanently, whether `setContinuous` is `true` or `false`.
It sets its status to `STOPPED`.

*For recoverable or temporary errors*, the replicator sets its status to `OFFLINE`, then:

* If `setContinuous=true`, it retries the connection indefinitely.

* If `setContinuous=false`, for a one-shot replication, it retries the connection a limited number of times.

The Couchbase Lite replicator treats the following error codes as temporary, and retries the connection when it receives them.

* `408`: Request Timeout

* `429`: Too Many Requests

* `500`: Internal Server Error

* `502`: Bad Gateway

* `503`: Service Unavailable

* `504`: Gateway Timeout

* `1001`: Domain name resolution error


[#load-balancers]
== Load Balancers


Couchbase Lite footnote:[From 2.0] uses WebSockets as the communication protocol to transmit data.
Some load balancers, such as nginx, do not enable WebSocket connections by default.
You might need to explicitly enable them in the load balancer configuration -- see xref:sync-gateway::load-balancer.adoc[Load Balancers].

By default, the WebSocket protocol uses compression to optimize for speed and bandwidth utilization.
Sync Gateway sets the level of compression, and you can tune it in the configuration file with xref:sync-gateway:ROOT:refer/config-properties.adoc#replicator_compression[`replicator_compression`].


[#lbl-cert-pinning]
== Certificate Pinning

Couchbase Lite for Java supports certificate pinning.

Applications can use certificate pinning to pin a host to its certificate.
The certificate is typically delivered to the client by an out-of-band channel and bundled with the client.
In this case, Couchbase Lite uses this embedded certificate to verify the trustworthiness of the server, such as Sync Gateway.
It no longer needs to rely on a trusted third party, commonly called the Certificate Authority.

The following steps describe how to configure certificate pinning between Couchbase Lite and Sync Gateway.

. xref:sync-gateway::security.adoc#creating-your-own-self-signed-certificate[Create your own self-signed certificate]
with the `openssl` command.
After completing this step, you should have 3 files: `cert.pem`, `cert.cer` and `privkey.pem`.

. xref:sync-gateway::security.adoc#installing-the-certificate[Configure Sync Gateway]
with the `cert.pem` and `privkey.pem` files.
After completing this step, Sync Gateway is reachable over `https`/`wss`.

. On the Couchbase Lite side, the replication must point to a URL with the `wss` scheme and configured with the `cert.cer` file created in step 1.
